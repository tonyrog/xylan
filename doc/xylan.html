What the user needs

# the api key is shown ONCE by xylan:generate_api_key/1
curl --cacert gw.pem -H "Authorization: Bearer sk-xyl-…" https://xylan3.example:11443/api/tags

# OpenAI compatible SDKs (ollama /v1)
export OPENAI_BASE_URL=https://xylan3.example:11443/v1
export OPENAI_API_KEY=sk-xyl-…
export SSL_CERT_FILE=gw.pem          # only for a self-signed gw certificate

What each party can see

  • Network between client and server: only TLS. Session keys, route info and auth are inside the tunnel.
  • xylan server: ssh and the user's TLS stream as ciphertext – never api keys or prompts.
  • Gateway (home): plaintext HTTP, checks the key, removes it, forwards to ollama on localhost.
  • Ollama: only reachable on 127.0.0.1, sees requests without api keys.

Configuration reference

Server (public node)

{xylan,
 [{mode, server},
  {id, "xylan3"},
  {port, [{ssh, "0.0.0.0", 46122},
          {ollama, "0.0.0.0", 11443}]},
  {client_port, 29390},      %% old, → none
  {data_port,   29391},      %% old, → none
  {client_tls_port, 29392},
  {data_tls_port,   29393},
  {tls_options,
   [{certfile, "/etc/xylan/server.pem"},
    {keyfile,  "/etc/xylan/server.key"}]},
  {max_tls_handshakes, 64},
  {max_tls_handshakes_per_ip, 8},
  {clients,
   [{"home",
     [{client_cert, "sha256:9A:3F:…"},
      %% and/or shared keys (both = cert+hmac)
      %% {server_key, 16#…256 bit…},
      %% {client_key, 16#…256 bit…},
      {require_tls, true},  %% implied by client_cert
      {route, [[{data, "SSH-2.0.*"}],
               [{dst_port, 11443}]]}]}]}]}

Client (home node)

{xylan,
 [{mode, client},
  {id, "home"},
  {server_ip, "xylan3.example"},
  {server_port, 29392},
  {server_tls,
   [{fingerprint, "sha256:21:09:88:…"},
    {certfile, "/etc/xylan/home.pem"},
    {keyfile,  "/etc/xylan/home.key"}]},
  %% {server_key, 16#…}, {client_key, 16#…},
  {route,
   [{ [{data, "SSH-2.0.*"}], [{port, 22}] },
    { [{data, ssl}],         [{port, 11443}] }]},

  {api_key_file, "/etc/xylan/api_keys.conf"},
  {api_gateways,
   [{ollama,
     [{port, 11443}, {ip, {127,0,0,1}},
      {target, {"127.0.0.1", 11434}},
      {tls, [{certfile, "/etc/xylan/gw.pem"},
             {keyfile,  "/etc/xylan/gw.key"}]},
      {host, rewrite},
      {max_connections, 64}]}]}]}

API key format

sk-xyl-LiOSGdJ4-S3mDjsLEhKhsJyOgBozZs1dh7Qes4mm1uyLKrcvYXUs0ivUUp

prefix · id (8 base62, public, used in logs/revoke) · secret (43 base62 = 256 bit) · crc32 (6 base62, catches typos). Stored as {"LiOSGdJ4", [{name,"ci"}, {hash,"sha256:…"}, {created,…}, {expires,{2027,6,30}}, {allow,[ollama]}]}. Accepted as Authorization: Bearer … or x-api-key: ….

Migration of existing nodes

  1. Server: generate_cert("server", …), add tls ports + tls_options. Old ports keep working.
  2. Per client: new keys generate_key(256) on both sides, server_tls with the fingerprint on the client, {require_tls,true} on the server.
  3. Optional: generate_cert("home", [{usage,client}]) on the client, add certfile/keyfile to server_tls, put the printed fingerprint as client_cert on the server, then remove the shared keys on both sides.
  4. When all clients are upgraded: {client_port,none}, {data_port,none}.

Security properties

  • Session key bound to channel type; must be routed before use.
  • Auth: HMAC-SHA256 with role labels, constant time compare, and/or pinned client certificate – then the server holds no client secret.
  • Data connections must present the same client certificate as the control channel.
  • A connecting socket can not close an active session before it authenticates.
  • TLS handshakes in separate processes, capped total and per ip.
  • Gateway: one request per connection, key headers removed, obs-fold rejected.
